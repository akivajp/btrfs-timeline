# btrfs-timeline

btrfs のスナップショットから、ファイルの過去の版をブラウザで辿って復元する —
Mac の Time Machine のような感覚で。

[English README is here](README.md)

> **状態: 開発初期。** 履歴の閲覧・版のプレビュー・復元は、CLI からも、
> スタンドアロンの Web UI からも、Cockpit モジュールとしても利用できます。
> [ロードマップ](#ロードマップ)を参照してください。

![Web UI。左がファイル一覧、右が選択したファイルの版の一覧で、各版にプレビューと復元のボタンが並んでいる](https://raw.githubusercontent.com/akivajp/btrfs-timeline/main/docs/screenshots/screenshot-history-ja.png)

1つのファイルに5行。まだ存在していなかった期間、それ以降に取った3つの内容、
そして現在のファイルです。元になったスナップショットは56個ありますが、
何も変わっていない分は行にする価値がありません。

## なぜ作るのか

snapper や btrbk、Timeshift で自動スナップショットを取っていれば、
**すべてのファイルのすべての過去版は既に手元にあります**。
しかし実際に1つ取り戻そうとすると、スナップショットの置き場所を知っていて、
どれが十分古いかを当てて、コマンドラインでファイルを見比べる必要があります。
できることはできますが、玄人向けの作業です。そしてこれこそが、
そもそもスナップショットを取っている理由そのものです。

既存のツールは、それぞれどこかで手前に止まっています。

| ツール | できること | 合わない点 |
| --- | --- | --- |
| [httm](https://github.com/kimono-koans/httm) | ZFS/btrfs の優れた対話的ファイル履歴 | CLI / TUI のみ |
| Btrfs Assistant, Snapper GUI | スナップショット管理 | デスクトップアプリ。ファイル単位の履歴ではない |
| Samba `vfs_shadow_copy2` | Windows エクスプローラの「以前のバージョン」 | Windows クライアントが前提 |
| Rockstor, OpenMediaVault | btrfs 対応の本格的な NAS Web UI | NAS 専用ディストリビューション。共有単位のロールバックでファイル単位ではない |
| Cockpit `storaged` | btrfs のファイルシステム/サブボリューム作成 | スナップショット閲覧は無し。マルチデバイス btrfs も非対応 |

**ブラウザを開いてパスを指定し、時間を遡る**、というものが存在しません。それを作ります。

## 設計

このプロジェクトは3つの形態での提供を想定しており、それらは1つのものを共有します。

```
btrfs_timeline/core/          ライブラリ: スナップショット検出・版の履歴・復元
btrfs_timeline/cli.py         全サブコマンドに --json を持つ CLI  <- 共有される契約
btrfs_timeline/web/static/    画面: index.html + app.js + style.css
                 transport.js   <- フロントエンドごとに差し替える唯一のファイル
   |- スタンドアロン Web   core を直接 import (同一プロセス)
   |- Cockpit モジュール   cockpit.spawn([... , "--json"], {superuser: "require"})
   `- デスクトップ GUI     core を import、または CLI 呼び出し
```

Cockpit モジュールには **サーバーサイドが存在せず**、実体は静的ファイルと
`manifest.json` だけで、ブラウザからプロセスを起動してシステムに触れます。
そのため、共有できるコアの形は「JSON を吐く CLI」しかありません。
全サブコマンドが `--json` を持つのはこのためで、その出力は公開 API として扱います。

画面はサーバーではなく**ブラウザ側で組み立てます**。Cockpit モジュールには描画を行う
サーバーが存在しないため、HTML に埋め込んだものは向こうで再利用できなくなるからです。
代わりに `app.js` はデータを `transport.js` から import し、フロントエンドごとに
差し替えるのはその1ファイルだけにしてあります
(こちらは `fetch('./api/history?…')`、あちらは `cockpit.spawn`)。
UI の残りの部分も、CLI と同じ JSON カタログから引く翻訳も、そのまま共有できます。

好みではなく実測から決まった判断が2つあります。

- **`btrfs subvolume list` を使わない。** これは root を要求します
  (非特権では `Operation not permitted`)。一方でスナップショット内のファイル自体は
  通常のパーミッションで読めます。検出を `/proc/self/mountinfo` とディレクトリ走査で
  行うことで、**履歴の閲覧に root が不要**になります。
- **重複排除は必須。** btrfs は CoW なので、変更していないファイルも
  スナップショットの数だけ現れます。作者の環境では 35 個のスナップショットが
  1 つの版に畳まれました。版は mtime とサイズで統合し、
  **ファイルが存在しなかった期間も独立した項目として残します** —
  そうしないと、削除されてから再作成されたファイルの履歴が繋がって見えてしまいます。

## インストール

```shell
pipx install btrfs-timeline          # CLI のみ。依存パッケージ無し
pipx install 'btrfs-timeline[web]'   # スタンドアロン Web UI 付き
```

Python 3.9 以降と Linux が必要です。履歴の閲覧に `btrfs-progs` は**不要**です。

## 使い方

```shell
# このファイルにはどんな版があるか
btrfs-timeline history ~/notes.md

# 機械可読出力 (スクリプトや Cockpit モジュール向け)
btrfs-timeline history ~/notes.md --json

# このパスを含むスナップショットと、そのレイアウト
btrfs-timeline snapshots ~/

# このシステムの btrfs マウント一覧
btrfs-timeline mounts

# ディレクトリの内容 (Web UI も同じ API を使っている)
btrfs-timeline browse ~/Documents --json

# その時点の内容。以降に削除されたものも含まれる
btrfs-timeline browse ~/Documents --snapshot 1729

# ある版と現在の差分 / 任意の2版の差分
btrfs-timeline diff ~/notes.md --from 2
btrfs-timeline diff ~/notes.md --from 2 --to 3

# 過去の版の内容 / 変更点
btrfs-timeline preview ~/notes.md --index 2
btrfs-timeline diff ~/notes.md --from 2

# Web UI を開く
btrfs-timeline serve
```

出力例:

```
/home/akiva/.gitconfig
  # 最初の観測           最後の観測               サイズ  SNAP数 状態
  1 2024-10-02 02:00:08  2025-01-01 00:00:00           -       3 (存在しない)
  2 2025-12-01 00:00:08  2026-03-01 00:00:00       268 B       4 ok
  3 2026-04-01 00:00:00  2026-09-23 01:00:00       297 B      28 ok
  4 -                    -                         297 B       - live
```

35 個のスナップショットが、意味のある3つの版と、
ファイルが作られる前の空白期間になっています。これが要点です。

## 復元

```shell
# スナップショット内の最新の版を、元のファイルの隣に復元する
btrfs-timeline restore ~/notes.md

# `history` の「#」列に出る版番号で指定する
btrfs-timeline restore ~/notes.md --index 2

# スナップショット ID で指定することもできる
btrfs-timeline restore ~/notes.md --snapshot 10129

# 何が起きるかだけ表示し、実際には何も変更しない
btrfs-timeline restore ~/notes.md --dry-run

# 別の場所に書く / 元のファイルを上書きする (上書き時も退避は残る)
btrfs-timeline restore ~/notes.md --to /tmp/notes.old.md
btrfs-timeline restore ~/notes.md --in-place
```

重要な性質が3つあります。

- **既定では何も上書きしません。** 復元先は元のファイルの隣の
  `notes.20260401T000008.md` になります。履歴ツールで最悪の事故は
  「古い版を取り戻そうとして、現在の内容を壊す」ことなので、
  確認プロンプトで防ぐのではなく既定動作から構造的に排除しています。
  上書きは `--in-place` を明示したときだけで、そのときも現在の内容は
  `notes.before-restore.<日時>.md` として退避されます
  (退避を省くには `--no-backup` と `--force` の両方が必要)。
- **コピーではなく reflink です。** `FICLONE` ioctl を使うため、
  スナップショットとエクステントを共有します。ファイルサイズに関わらず一瞬で終わり、
  追加の容量も消費しません。復元先が別のファイルシステムの場合は通常のコピーに落ち、
  どちらで行ったかは出力に表示されます。
- **書き込みは原子的です。** 復元先と同じディレクトリの一時ファイルに書いてから
  `rename(2)` で差し替えるので、途中で中断しても書きかけのファイルは残りません。

## Web UI

```shell
pipx install 'btrfs-timeline[web]'
btrfs-timeline serve                       # http://127.0.0.1:8088/
btrfs-timeline serve --root ~/Documents    # このディレクトリ配下だけを閲覧可能にする
btrfs-timeline serve --read-only           # 履歴の閲覧のみ。復元は無効
```

左でファイルシステムを辿り、ファイルをクリックすると右に版の一覧が出ます。
決める前に各版の中身をプレビューでき、ボタン1つで復元できます。
復元は必ず先に dry-run を表示し、**どこに何を書くのか**と
**現在の内容をどこに退避するのか**を見せてから確認を取ります。

**時間軸は1本だけで、モードはありません。** この画面がすることは全て
「パス」と「時点」の組み合わせで表現されています。

- **ディレクトリ**をクリックすると、そのディレクトリの履歴も出ます。
  版を選ぶと、左の一覧が**その時点の内容**に切り替わります。
- **以降に削除されたもの**は取り消し線付きでそこに現れます。
  現在のファイルシステムには存在しないため、辿り着く経路はここだけです。
  そこから先の履歴・復元は、他のファイルと全く同じように動きます。
- プレビューのペインはそのまま**差分**にもなります。現在との比較が既定で、
  切り替えの隣のセレクトで任意の版とも比較できます。

これらのためにタブは1つも増やしていません。機能ごとに画面を分けると、
同じ「過去を見る」操作を3通り覚えることになるためです。

画面上の設定は2つだけで、いずれもブラウザごとに記憶されます。
**表示言語** (CLI と同じカタログから選びます) と、**隠しファイルを表示するか**です。
後者は既定でオフにしてあります。ホームディレクトリの中身はほとんどがドットファイルで、
目的のものがその中に埋もれてしまうためです。

既定ではループバックのみで待ち受けます。それ以外のアドレスに対しては
`--auth USER:PASSWORD` (環境変数 `BTRFS_TIMELINE_AUTH` も可) が無い限り**起動を拒否**します。
到達できる誰もがファイルを読み、上書きまでできてしまうためです
(意図的に公開する場合は `--allow-no-auth`)。
復元は `POST` のみで、`Origin` が別サイトのリクエストは拒否します。
BASIC 認証だけでは、他サイトがブラウザに代理でリクエストを送らせるのを防げないためです。

サーバーはあなたの権限で動くので、あなたが読めるものしか読めません。
root は不要です — `btrfs subvolume list` を使わないことの狙いがここにあります。

## Cockpit モジュール

既に [Cockpit](https://cockpit-project.org/) を使っている場合は、同じ画面を
その中から開けます。

```shell
btrfs-timeline cockpit install            # ~/.local/share/cockpit に設置
btrfs-timeline cockpit install --system   # /usr/share/cockpit に全ユーザー向けで設置
btrfs-timeline cockpit uninstall
```

Cockpit を開き直して、ツールの中の **ファイル履歴** を選んでください。
再起動もサービスの追加も必要ありません。メニューの項目名も他と同じカタログから
訳されるので、Cockpit を使っている言語に追随します。

中身は `index.html`・`app.js`・`i18n.js`・`style.css` をそのままコピーしたもので、
書き換えは一切していません。**違うのは `transport.js` だけ**で、HTTP API の代わりに
CLI を呼びます。

```js
cockpit.spawn([...COMMAND, 'history', path, '--json'])
```

**特権昇格は要求しません。** スナップショットの閲覧に root は要らず、復元はログイン中の
利用者の権限で書くため、それ以上を求める理由がないからです。
テストでは本物の `app.js` を両方の経路で走らせ、**最終的な画面が一致すること**を
検証しています。

`cockpit.spawn` はシェルの `PATH` を引き継がないため、`install` は
**実行した環境の絶対パス**を記録します。`btrfs-timeline` 自体の入れ方を変えたときは、
設置し直してください。

## デバイス

```shell
btrfs-timeline devices
btrfs-timeline devices --json
```

各ファイルシステムがどのデバイスで構成されているか、割り当ての種類ごとの
RAID プロファイル、デバイスの欠損の有無、実行中の操作、そしてデバイス毎の
エラーカウンタを表示します。最後のものは、ディスク・ケーブル・電源のいずれかが
弱っていることを教えてくれる数字です。

![ダッシュボード。どのサブボリュームがどこにマウントされているか、型番と温度つきのデバイス一覧、割り当てごとのプロファイル、そしてそれを読むために実行したコマンド](https://raw.githubusercontent.com/akivajp/btrfs-timeline/main/docs/screenshots/screenshot-devices-ja.png)

**root は不要です。** `btrfs filesystem show` は意図的に使っていません
(あれは生のブロックデバイスを開くため、非特権では `Permission denied` になります)。
ここで使うのは `/sys/fs/btrfs/` と `btrfs device stats --format json` だけで、
どちらも通常の利用者が読めます。履歴の閲覧に root を要らなくしたのと同じ理由です。

**裏で実行したコマンドは、結果と危険度を添えて必ず表示します。**

```
  実行したコマンド: btrfs --format json device stats /  [安全]
```

この表示は飾りではありません。各操作は危険度を申告します
(**安全**=何も変えない、**状態を変更**=変えるが中断・巻き戻せる、
**危険**=失敗するとデータを失いうる)。そして **危険な操作は、確認を取るまで
そもそも実行できません**。変更を伴う操作はこの上に載ります —
次が scrub と balance、その次がデバイスの追加・取り外し・置換です。

## メンテナンス

```shell
btrfs-timeline scrub status /home
btrfs-timeline scrub start /home --sudo
btrfs-timeline balance start /home --usage 20 --sudo
```

scrub は全ブロックを読んでチェックサムと照合し、別コピーがあるものを修復します。
balance はチャンクを書き直してデバイス間の割り当てを均します。`--usage 20` は
使用率 20%% 未満のチャンクだけを対象にするもので、空きの断片化に対する定石であり、
全体 balance より格段に軽くて済みます。

**何を実行するのかを示さずに、確認せずに走るものはありません。**

```
$ btrfs-timeline scrub start /home
実行するコマンド: btrfs scrub start /home
  危険度: 状態を変更 — /home の全ブロックを読み、別コピーがあるものは修復する
実行しますか? [y/N]
```

各操作は危険度を申告します（**安全**=何も変えない、**状態を変更**=変えるが中断・再開できる、
**危険**=データを失いうる）。確認を省くのは安全な操作だけです。
**端末が無く確認を取れない場所では、「はい」とみなさずに拒否します**（意図的な場合は `--yes`）。

これらの操作には root が必要ですが、**勝手に権限昇格はしません**。
`sudo` を付けた実行すべきコマンドをそのまま提示して止まり、`--sudo` を明示したときだけ
自分で付けます。**表示する文字列と実行する文字列は同一**なので、
確認した内容と実際に走るものが食い違うことはありません。

`scrub status` は非特権でも試みますが、**当てにはできません**。
btrfs は `/var/lib/btrfs/scrub.status.<UUID>` を root 専用で書くため、
**一度も scrub していない間は読め、一度走らせた後は `Permission denied` になります**。
前もって断らないのは、読める場合が実在するからで、
失敗したときは `sudo` を付けた再実行用のコマンドを示します。
`balance status` は最初から root が必要です。

### ブラウザから

`btrfs-timeline serve` にダッシュボードのページがあり、履歴の画面から辿れます。
同じ情報を表示し、エラーを抱えたデバイスや欠損したデバイスは埋もれないように
目立たせ、scrub の状態も出します。

**この画面は意図的に読み取り専用です。** scrub と balance には root が必要で、
このサーバーは利用者の権限で動きます。**押しても必ず失敗するボタンは、
無いほうがましです。** 代わりに、端末で実行すべきコマンドを `sudo` 付き・危険度つきで
CLI と同じ形で表示します。特権が要る操作は、そのためのチャネルを持つ
Cockpit モジュール側が扱うべき領分だと考えています。

### デバイス

```shell
btrfs-timeline device add /dev/sdd --path /mnt --sudo
btrfs-timeline device remove /dev/sdc --path /mnt --sudo --confirm /dev/sdc
btrfs-timeline device replace /dev/sdc /dev/sdd --path /mnt --sudo --confirm /dev/sdd
```

これらは失敗するとプールごと失いうるため、**危険**と申告される唯一の操作群で、
**`--yes` では通りません。** 確認はデバイス名そのものを入力する形で行います
（リポジトリを消すときに名前を打たせるのと同じ考え方です）。
これが防ぐのは「実行する気が無かった」ことではなく、
**別のディスクを指していることに気付かないまま実行する**ことです。

`replace` で入力するのは **target（上書きされる側）** です。
source は抜ける側で中身は移されますが、target は持っていたものを全て失います。
**危険に晒されている側を確認させなければ、確認の意味がありません。**

`add` は **状態を変更** に留めています。btrfs は既存のファイルシステムがある
デバイスを拒否するので、打ち間違いはそこで弾かれるためです。
`--force` はその確認を外すので、危険度が上がり名前の入力を求めます。

なお、**合言葉を持たない「危険」な操作は組み立てられません**。
書き忘れは `ValueError` になり、確認が静かに弱まることはありません。

各ファイルシステムについて、**どのサブボリュームがどこにマウントされているか**を
表示します。`/home` の正体が `subvol=/@home` であるという関係は btrfs が隠しており、
パスの羅列では伝わらない部分です。あわせて各デバイスの型番と温度も出します。

**マウント先ごとのデバイスは表示しません。** btrfs ではどのマウント先も全デバイスに
支えられており、`mountinfo` に出るデバイスは「マウント時にどのノードを指定したか」を
記録しているに過ぎません。これを列にすると全行が同じ 1 台になり、しかも
**そのマウントがそこに載っていると読めてしまいます**。関係は文章で 1 度述べ、
割り当ての表には「何台に分散しているか」を出しています。
デバイスごとの内訳（どの割り当てがどのディスクにどれだけ載っているか）には
チャンク情報が必要で、つまり root が要ります。
**Cockpit モジュールでは、Cockpit 自身の仕組みでこれを扱います** —
その呼び出しだけ `superuser: "try"` を使うので、セッションに管理アクセスがあれば
内訳が出て、無ければ単に出ないだけです。モジュール内の他の操作は一切権限を求めません。

スタンドアロンのサーバーでは表示せず、`btrfs device usage` をコマンドとして提示します。

内訳が出せないときは**その理由を表示し、理由は経路ごとに書き分けます**。
Cockpit で制限付きアクセスなら、**Cockpit 自身のヘッダーにある切り替え**を指し示し、
それを有効にすると**画面が自動で読み直します**。こちらから昇格を促すことはしません。
スタンドアロンでは Cockpit モジュールへ誘導します。
**「権限が足りない」と「この経路では無理」は別の状況**であり、
同じ文言で済ませても誰の役にも立たないためです。

なお**特権が必要な「操作」**（scrub・balance・デバイスの変更）は、
どちらの経路でも引き続き端末から実行します。昇格しているのは内訳の読み取りだけです。
そこで表示しようとすると、**ファイルを読み書きする Web サーバーを root で動かす**か、
**独自の権限昇格の仕組みを作る**かのどちらかになります。
ディスクの割り当て内訳のために払う代償としては大きすぎますし、
この問題は Cockpit が既に正しく解いています。

**温度は hwmon から非特権で読んでいます**（NVMe ドライバが提供し、SATA でも
`drivetemp` が読み込まれていれば出ます）。高温の警告は **デバイス自身が申告する
危険域** と比べて出しており、こちらで何度と決めてはいません。
このツールが勝手に決めた閾値は、いずれ誰かのディスクで外れます。
**外れる警告は、読まれなくなります。**

消耗度・代替セクタ数・稼働時間は sysfs では読めません。そこは `smartctl` の領分で
root が必要です。ダッシュボードは、**エラーが記録されているデバイスについてのみ**
そのコマンドを提示します。代わりに実行したり、普段は不要な権限を要求したりはしません。

## 翻訳

メッセージは [`btrfs_timeline/locales/`](btrfs_timeline/locales/) に置かれた JSON の
カタログから実行時に引いています。`en.json` が参照カタログで、
**カタログに無いキーは自動的に英語にフォールバック**するため、
訳しかけの状態でも1行目から役に立ちます。

```shell
btrfs-timeline history ~/notes.md --lang ja   # この実行だけ
BTRFS_TIMELINE_LANG=ja btrfs-timeline ...     # このシェルの間
```

どちらも指定しない場合は `LC_ALL` / `LC_MESSAGES` / `LANG` から決まり、
最終的に英語に落ちます (`LANG=C` は英語とみなします)。
翻訳されるのは人間向けの出力だけです。`--json` の出力はどの言語でも完全に同一で、
これはフロントエンドやスクリプトが読むものだからです。

**画面に出るものをサーバー側で訳すことはしません。** 画面はメッセージのキーと
引数を受け取り、手元のカタログで訳します。サーバーの言語は起動時に環境から決まるのに対し、
読む人の言語は画面で選ばれるもので、これを混ぜると**一文だけ違う言語が紛れ込みます**。

### 言語を追加するには

`en.json` を `<言語コード>.json` にコピーして値を訳すだけです
(言語コードは `de` のような ISO 639-1、または `pt_br` のような地域別。
地域別のカタログが無ければ `pt` に落ちます)。
まず `language.name` を、**その言語自身による呼び名** (`Japanese` ではなく `日本語`) にしてください。
この文字列が Web UI の言語セレクトに並ぶため、その言語しか読めない人が
自分の言語を見つけられる必要があります。**コードには一切触れる必要がありません。**
新しい言語は自動的に認識され、`--lang` が受け付ける値にも言語セレクトにも加わります。

テスト (`pytest tests/test_i18n.py`) が次の2点を機械的に検査します。

- `en.json` の全キーが揃っていること。余分なキーが無いこと。
- プレースホルダの**名前**が一致していること (`{path}`、`{index}`)。
  文中での順序は自由に変えて構いません。名前付きにしてあるのは、まさにそのためです。

表の桁揃えは文字数ではなく**端末上の表示幅**で行っているため、
日本語などの全角文字を使っても崩れません。

gettext ではなく JSON を採用している理由: `.po` は `.mo` へのコンパイル工程が必要であり、
また Web UI と Cockpit モジュールはブラウザ上で描画するため `.mo` を使えません。
Python と JavaScript の双方から読める形式を1つにしておくことで、
訳文が二重管理になるのを防いでいます。

## 対応するスナップショットのレイアウト

| レイアウト | パスの形 | 主な出所 |
| --- | --- | --- |
| snapper | `<マウント>/.snapshots/<番号>/snapshot` + `info.xml` | snapper |
| flat | `<マウント>/.snapshots/<名前>` | btrbk, Timeshift, 手動運用 |

取得日時は、snapper の `info.xml` (タイムゾーン表記が無いが **UTC**)、
ディレクトリ名に埋め込まれた日時、ディレクトリの mtime の順で判定します。

## ロードマップ

1. **ファイル履歴ブラウザ / スタンドアロン Web UI** — 実装済み
2. **Cockpit モジュール** — 実装済み。同じ CLI と同じ画面を使い、
   差し替えるのは `transport.js` だけ
3. **ダッシュボードとデバイス管理** — 実装済み
4. **デスクトップ GUI**

デバイス管理 (3) は失敗するとファイルシステムを壊しうるもので、
履歴を読むのとは risk の種類が違います。モジュールも権限も分離したままにします。

## 注意点と制限

- シンボリックリンクは**現在の**ファイルシステム上で解決するため、履歴はリンク先の
  実体を辿ります (dotfiles 運用で有用)。一方、スナップショット内のリンクは決して
  辿らないので、スナップショットがライブの内容を過去の版として報告することはありません。
- 版の比較は mtime とサイズで行い、内容のハッシュは取りません
  (全ファイルの全版を読み込むことになるため)。
- ディレクトリ単位の復元には未対応で、個別のファイルのみが対象です。
  ある時点のディレクトリの内容を見て、その中のファイルを1つずつ復元することはできますが、
  「このディレクトリを丸ごと戻す」操作はありません。
  一部だけを黙って復元するより、断る方が安全だと考えています。
- ディレクトリの履歴は、btrfs が保存しているディレクトリ自身の mtime から得ています。
  これは項目の追加・削除・改名で変化し、**中のファイルが編集されただけでは変化しません**。
  そのためディレクトリの版は「何が出入りしたか」を示します。
  削除されたものを探すにはこの粒度が適切で、編集の履歴はファイル自身の履歴を見てください。
- 復元したファイルは元のパーミッションと mtime を引き継ぎますが、所有者は引き継ぎません。
  `chown` には root が必要で、このツールは非特権で動かすことを前提にしているためです。
- `devices` は「各デバイスを btrfs がどれだけ使っているか」は表示しません。
  これにはチャンク情報が必要で、ここで唯一 root を要求する部分になります。
  列を1つ埋めるために root を求める価値は無いと判断しました。
- btrfs の RAID 5/6 は上流で依然として本番向けとは見なされていません。
  このツールはその事情を変えるものではありません。

## 代替となるツール

ブラウザではなくターミナルで済ませたい場合は
[httm](https://github.com/kimono-koans/httm) が成熟していて高速で、ZFS にも対応しています。
本格的な NAS アプライアンスが欲しい場合は [Rockstor](https://rockstor.com/) や
[OpenMediaVault](https://www.openmediavault.org/) を使ってください。
